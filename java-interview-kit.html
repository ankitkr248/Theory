Senior engineer · ~5 years · Java 9 → 25

What they'll actually ask you

22 questions covering the language and library changes from Java 9 to 25 — the parts a senior interview actually probes. Each card is the question as it gets asked, the answer worth giving, the code, and the follow-up that separates a memorised answer from a used one.

The 6 three-dot cards are the ones to know cold. Records, pattern matching and virtual threads come up in almost every Java interview at this level; the rest is depth you deploy when the conversation goes there.
01LanguageJava 21

Explain virtual threads. When would you actually use them?

A virtual thread is a java.lang.Thread scheduled by the JVM instead of the OS. It costs roughly an object to create rather than ~1 MB of stack, and it is mounted on a small pool of platform carrier threads only while it is running — when it blocks, the JVM parks the continuation on the heap and hands the carrier to someone else.

The point is not that they are faster; it is that plain blocking, thread-per-request code now scales to hundreds of thousands of concurrent I/O operations without a reactive rewrite. Use them for I/O-bound concurrency. Do not use them for CPU-bound work — you still have only N cores, so a fixed pool is still correct there.

Why shouldn't you pool virtual threads?

Because pooling exists to ration an expensive resource, and virtual threads are the cheap one — pooling them is like pooling an Integer. Worse, it reintroduces exactly the ceiling you removed. Pool the scarce thing behind them: the database connection, the rate-limited API.

What is pinning?

Before Java 24, a virtual thread that blocked inside a synchronized block could not unmount, so it held its carrier thread hostage. With a carrier pool sized to the core count, a handful of those will stall your whole application. On Java 21–23 the fix was to convert hot paths to ReentrantLock; JEP 491 in Java 24 removed the limitation for object monitors. Native frames (JNI / FFM downcalls) still pin. Diagnose with -Djdk.tracePinnedThreads=full or the jdk.VirtualThreadPinned JFR event.

What about ThreadLocal?

A million threads means a million copies — thread-locals used as caches become a memory problem rather than an optimisation. That is the problem scoped values (final in Java 25) were designed to solve.

If threads are free now, what is the new bottleneck?

Everything downstream. Virtual threads will happily queue fifty thousand requests against a twenty-connection pool. Concurrency still has to be bounded somewhere — a Semaphore or a bulkhead in front of each dependency — you have just moved the limit off the thread pool, where it used to sit by accident.

02LanguageJava 16

What is a record, and when would you use one over a class?

A transparent carrier for immutable data. The compiler derives the private final fields, the canonical constructor, the accessors (x(), not getX()), plus equals/hashCode/toString from the component list. Records are implicitly final and cannot extend a class.

Reach for one for DTOs, API request/response types, value objects, map keys, and intermediate shapes inside a stream. Do not use one for a JPA entity — those need a no-arg constructor and mutable state — or anywhere you need inheritance.

Are records immutable?

Shallowly. The reference fields are final; what they point at need not be. This is the follow-up that catches people out — verified behaviour below. Defensively copy in the compact constructor, and if the component is still mutable, in the accessor too.

Records vs Lombok @Value?

Records are a language feature: no annotation processor, no build-order surprises, semantics guaranteed by the spec, and — the real difference — they can be destructured by record patterns, which Lombok classes cannot. Lombok is still more flexible (builders, mutable @Data, partial generation).

03LanguageJava 21

How does pattern matching for switch change the way you write code?

It lets a switch dispatch on the shape of a value, not just its constant value. You get type patterns as case labels, when guards, record patterns that destructure, and an explicit case null. In practice it replaces long if / else if (x instanceof …) chains and, very often, the visitor pattern.

Over a sealed type the switch is checked exhaustive, so you can drop default — and adding a new subtype then becomes a compile error in every switch that handles it, instead of silently falling through to a default branch.

Gotcha

A pattern switch throws NullPointerException on a null selector unless you write case null. That is deliberate — it preserves the behaviour of every switch written before Java 21, so adding patterns to an existing switch does not silently change how nulls behave.

When is a sealed interface plus a pattern switch better than polymorphism?

This is the expression problem, and the honest answer names both sides. Polymorphism makes it cheap to add a new type and expensive to add a new operation across all types; a sealed hierarchy plus pattern matching inverts that. So: use polymorphism when the behaviour genuinely belongs to the data and new implementations arrive often. Use sealed + patterns when the set of types is closed and stable, and the operations keep multiplying — pricing rules, serialisation, rendering, anything a consumer defines rather than the data owner.

04LanguageJava 17

What problem do sealed classes solve?

They let a type declare its complete set of permitted subtypes, so the compiler knows the hierarchy is closed. Before this, an interface said 'anyone may implement me' and there was no way to express 'this value is one of exactly these three things'.

Two payoffs: exhaustiveness checking in switch, and a modelling vocabulary for closed domains — PaymentMethod, Result, an event union. Every permitted subtype must itself be final, sealed, or explicitly non-sealed; there is no fourth option, and that is what makes the exhaustiveness check sound.

What do you get from sealed types plus records?

Algebraic data types: a sum type (the sealed interface) of product types (the records), consumed by an exhaustive pattern switch. That combination is the whole point of the language work from Java 14 to 21 — records (16), instanceof patterns (16), sealed classes (17), pattern switch and record patterns (21) are one feature delivered in five instalments.

05LanguageJava 16

What is flow scoping in instanceof pattern matching?

The binding variable is in scope exactly where the compiler can prove the test succeeded — which is more places than people expect. It works on the right-hand side of &&, and it works after a negated test that returns early, because at that point the only way to still be executing is for the test to have passed.

06LanguageJava 14

Switch expression versus switch statement — what actually changed?

Four things. The arrow form has no fall-through, so no missing-break bugs. A case can list multiple labels. The whole switch can be an expression that produces a value, with yield for block-bodied arms. And a switch expression must be exhaustive.

The exhaustiveness point is the one worth making: over an enum or a sealed type, drop the default and the compiler will fail the build when someone adds a new constant. With a default in place, that same addition silently takes the default branch at runtime.

07LanguageJava 10

What does var do — is Java dynamically typed now?

No. It is compile-time local variable type inference. The variable has exactly one static type, fixed at the declaration and inferred from the initialiser; the compiled bytecode is identical to writing the type out. It works only for local variables with an initialiser, the index of an enhanced for, and try-with-resources — never for fields, parameters or return types.

When would you not use it?

When the initialiser does not tell the reader the type — var result = service.process(input) is worse than the explicit form. Remember that code review happens in a diff, not in an IDE. Good uses: long generic types, obvious constructor calls, loop variables. Bad uses: hiding the difference between int and long, or between List and ArrayList when it matters.

08LanguageJava 15

How does indentation work inside a text block?

The compiler strips incidental whitespace. It looks at every non-blank line and the line containing the closing delimiter, takes the minimum indentation across all of them, and removes that much from every line. So the position of the closing """ is what sets the left margin — which is the part people get wrong.

09LanguageJava 22

What is the Foreign Function & Memory API, and what does it replace?

The supported way to call native code and manage off-heap memory from pure Java — it replaces JNI (no C glue code, no separate build step) and sun.misc.Unsafe's memory access, which is deprecated for removal. Final in Java 22 after nine releases of incubation and preview.

The safety mechanism worth naming is the Arena: it gives a memory segment a deterministic lifetime, so touching a segment after its arena closes throws instead of corrupting the heap.

10LanguageJava 25

What does 'Hello World' look like in Java 25?

Two features finalised in 25 make this the shortest it has ever been: compact source files (no class declaration, instance main with no parameters, java.base implicitly imported, and a new java.lang.IO class) and module import declarations.

The motivation is teaching — you no longer have to explain public static void main(String[] args) before printing a line. Worth knowing because it signals you follow the language, and because import module java.base is genuinely useful in scripts and tests.

11Collections & StreamsJava 9

Difference between List.of(), Arrays.asList() and Collections.unmodifiableList()?

Three different things that all look immutable and are not.

List.of() — genuinely immutable, fixed, and it rejects nulls. Arrays.asList() — a fixed-size view over the array: set() works and writes through to the array, add() throws, nulls are allowed. Collections.unmodifiableList() — an unmodifiable view over a mutable list: you cannot change it through that reference, but changes to the backing list show through.

Why does List.of reject nulls?

It keeps the contract simple and permits optimisations, and a null inside an immutable collection is nearly always a bug. Related: Map.of iteration order is deliberately randomised per JVM run, so code that accidentally depends on it will fail in an obvious way rather than in production.

12Collections & StreamsJava 16

Difference between stream.toList() and collect(Collectors.toList())?

toList() (Java 16) returns an unmodifiable list. Collectors.toList() makes no guarantee about the implementation, but in practice always returns a mutable ArrayList. So the shorter form is not a drop-in replacement: migrating code that mutates the result will start throwing UnsupportedOperationException at runtime, not at compile time.

If you need a mutable result, be explicit about it.

13Collections & StreamsJava 9–24

What has been added to Stream and Optional since Java 8?

Worth knowing because most people's stream vocabulary stopped at Java 8. The additions fall into three groups: short-circuiting operations that filter could not express, terminal conveniences, and — in Java 24 — a genuine extension point.

14Collections & StreamsJava 21

What are sequenced collections, and why did they take 25 years?

Java has had ordered collections since 1.2 with no common way to ask for the first or last element: list.get(0), deque.getFirst(), sortedSet.first(), and for LinkedHashSet you had to take an iterator. Java 21 retrofits three interfaces — SequencedCollection, SequencedSet, SequencedMap — onto the existing types with a uniform API, including reversed().

15Collections & StreamsJava 24

What are stream gatherers?

Custom intermediate stream operations — the extension point Stream never had. Collector could only terminate a pipeline, so windowing, running totals and stateful de-duplication had to be done outside the stream. Gatherer fixes that. Final in Java 24 after two previews.

16ConcurrencyJava 21–25

Do virtual threads make CompletableFuture obsolete?

No, but the default flips. If you reached for CompletableFuture purely to avoid blocking a scarce thread, that reason is gone — plain blocking code on a virtual thread is simpler, and gives you real stack traces and working debuggers, which async pipelines never did.

CompletableFuture is still the right tool for composing results that arrive independently, and for APIs that are genuinely non-blocking underneath. For the common fan-out / fan-in case, structured concurrency expresses it more clearly and handles cancellation for you.

17ConcurrencyJava 25

What replaces ThreadLocal in a virtual-thread world?

Scoped values, final in Java 25 after four previews. A scoped value is immutable and has a bounded lifetime: it is bound only for the duration of a run() or call(), so there is nothing to leak and no remove() to forget in a finally block. With a million threads, that difference is the entire argument.

Gotcha

Inheritance is narrower than it was during preview. Only subtasks forked from a StructuredTaskScope inherit bindings — a task submitted to a plain newVirtualThreadPerTaskExecutor() does not (verified on JDK 25.0.3: the child sees an unbound value). A lot of blog posts still say otherwise.

18Runtime & JVMJava 9–25

Which garbage collector would you choose, and what changed since Java 8?

Answer by workload rather than by naming a favourite.

G1 — the default since Java 9, and the right answer for most services: balanced, tunable with one knob. ZGC — large heaps or strict latency budgets; pauses stay sub-millisecond regardless of heap size, generational since 21 and the only mode since 23. Serial — small containers, low core counts, short-lived jobs; frequently the best choice and almost always forgotten. Parallel — pure batch throughput where pauses do not matter.

The change that bites on upgrade is that Java 8 defaulted to Parallel and Java 9 defaults to G1, so old tuning flags are now being applied to a different collector.

What else changed in the runtime between 9 and 25?

Compact strings (9) roughly halved the footprint of Latin-1 strings. Unified -Xlog (9) replaced every ad-hoc logging flag. Container awareness (10) stopped the JVM sizing its heap against the host. Application CDS (10/13) and then the AOT cache (24/25) cut startup. Compact object headers (25) shrink every object header from 96–128 bits to 64.

19Runtime & JVMJava 25

What is worth upgrading from Java 21 to 25 for?

Very little of it is syntax — the case is startup, memory and finished concurrency primitives.

AOT cache (JEP 483/514/515): a training run records class loading, linking and method profiles, and later runs map that in. Commonly 30–40% faster startup on framework-heavy applications for no source change. Compact object headers (JEP 519): typically 10–20% smaller live sets. Scoped values go final. And JEP 491 in Java 24 removed virtual-thread pinning on synchronized, which is the single most useful fix for anyone who adopted virtual threads on 21.

Gotcha

The AOT cache is tied to the exact JDK build, class path and flags. Generate it in the same build step that produces the artefact and treat it as a build output — do not commit it.

20Runtime & JVMJava 9

What is the module system, and have you actually used it?

Be honest here, because most interviewers know the answer. Very few applications modularise their own code; the JDK modularised, and what you feel downstream is strong encapsulation — internal JDK classes stopped being reachable, which is the source of most 8 → 11 pain.

The mechanics: module-info.java declares requires (what I need), exports (what others may use), and opens (what may be reflected into). Anything not exported is inaccessible at compile and run time. The real payoff, when you take it, is jlink.

Why did upgrading from 8 to 11 break everyone's build?

Two reasons. JEP 320 removed the Java EE modules, so javax.xml.bind (JAXB), javax.annotation and javax.activation vanished — they are now ordinary Jakarta dependencies. And reflective access into JDK internals started warning in 9 and throwing by default in 16.

21MigrationJava 8–25

We're on Java 8 (or 11, or 17). Make the case for upgrading, and tell me what breaks.

Answer per jump, because the risk profile is completely different at each step. The order below is by how much trouble you should budget for.

8 → 11The hard oneJava EE modules removed (JAXB, javax.annotation, javax.activation) — add the Jakarta artifacts. Reflective access into JDK internals starts warning. Every GC logging flag replaced by -Xlog, so the JVM may refuse to start. Default GC changes from Parallel to G1. java.version format changes.
11 → 17Mostly mechanical--illegal-access=permit was removed, so every opening must be named explicitly with --add-opens / --add-exports. Reflection that only warned on 11 now throws. In return you get records, sealed classes, instanceof patterns, text blocks and switch expressions all permanent.
17 → 21Low risk, highest rewardAlmost nothing breaks. You get virtual threads, pattern matching for switch, record patterns and sequenced collections. This is the jump with the best ratio in the whole list. One gotcha: Stream.toList() returns an immutable list.
21 → 25Startup and memoryAOT cache, compact object headers, generational Shenandoah, scoped values final, and virtual-thread pinning on synchronized fixed in 24. Native access must now be declared with --enable-native-access.

How would you de-risk it?

Run the new JDK before you compile for it — the JVM is far more backward-compatible than the toolchain, so start by running your existing Java 8 artefact on 21 and fixing what falls over. Then move the compiler target. Use the readiness flags in CI: --sun-misc-unsafe-memory-access=deny, --illegal-native-access=deny, --finalization=disabled — each one tells you today what a future release will enforce.

22MigrationJava 23

Have you used string templates?

A trick question if the interviewer is current, and a good one to get right. String templates were previewed in Java 21 and 22 and then withdrawn entirely in Java 23 — the first time a Java language preview has been abandoned outright. The design had not converged on how the processor is selected or how templates interact with the type system. Nothing has been targeted since.

The broader point this tests: know the difference between final, preview and incubating. A preview feature needs --enable-preview, can change or vanish, and produces class files pinned to the exact release that compiled them — it does not belong in production.

What is still in preview or incubating in Java 25?

Preview: stable values, structured concurrency (fifth preview), primitive types in patterns (third), PEM encodings. Incubating: the Vector API, now in its tenth incubator round — it is waiting on Project Valhalla's value classes.

Rapid fire

One-line answers for the last twenty minutes before the call.

Which Java versions are LTS?

8, 11, 17, 21, 25 — a new one every two years since 17.

Records: getX() or x()?

x(). The component name, no get prefix.

Can a record extend a class?

No. Records are implicitly final and already extend java.lang.Record. They can implement interfaces.

Is var a keyword?

No — it is a reserved type name, so a variable or method called var still compiles.

What is the default GC?

G1, since Java 9. Java 8 defaulted to Parallel.

Default charset?

UTF-8 everywhere since Java 18, regardless of the OS locale.

Does a switch expression need a default?

Only if it is not already exhaustive. Over an enum or a sealed type, omit it deliberately so new subtypes break the build.

What does sealed require of its subtypes?

Each must be final, sealed, or non-sealed. No fourth option.

Virtual thread stack size?

It has no fixed stack — the continuation lives on the heap and grows as needed. Roughly a kilobyte to start, against ~1 MB for a platform thread.

How many carrier threads by default?

Runtime.availableProcessors(), in a dedicated ForkJoinPool. Tune with jdk.virtualThreadScheduler.parallelism.

Is Stream.toList() mutable?

No. Collectors.toList() is, in practice — that is the migration gotcha.

Does reversed() copy?

No, it returns a live view. Changes to the original show through.

What does Optional.stream() do?

Yields zero or one element, so flatMap(Optional::stream) flattens a stream of Optionals.

Which release removed the Security Manager?

Permanently disabled in Java 24; deprecated for removal back in 17.

What happened to sun.misc.Unsafe?

Memory-access methods deprecated in 23, warn at runtime in 24. Replacements: VarHandle (9) and the FFM API (22).

Text block: what sets the left margin?

The minimum indentation across all non-blank lines and the closing delimiter line.
